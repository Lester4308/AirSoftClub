==================================================
3. AUTHORITATIVE NUMERIC MODEL
==================================================

Не використовувати float/double для authoritative combat calculations.

Реалізувати deterministic fixed-point / scaled-integer numeric approach.

Потрібно мати централізований abstraction/value type або чітко документований integer scale.

Приклад concept:

10000 = 1.0000

Але конкретну реалізацію вибери так, щоб:

- arithmetic була deterministic;
- overflow був контрольований;
- rounding rules були явними;
- tests покривали boundaries.

Не розкидати magic scaling constants по коду.

==================================================
4. SEEDED RNG
==================================================

Реалізувати власний deterministic seeded RNG abstraction.

НЕ використовувати:

UnityEngine.Random
System.Random як прихований implementation detail без гарантії compatibility/reproducibility.

RNG має:

- приймати explicit seed;
- давати reproducible sequence;
- мати deterministic integer/range operations;
- бути injectable/testable.

Match із тим самим:

MatchConfig
TeamSnapshotA
TeamSnapshotB
Seed
RulesetVersion

повинен давати той самий MatchResult.

==================================================
7. HP MODEL
==================================================

Fighter має:

MaxHP
StartingHP / CurrentHP inside battle.

Для offensive fixture:
Starting HP може бути менше Max HP.

Для defense fixtures:
caller передає snapshot із 100% Max HP.

Combat core НЕ повинен сам знати про live recovery timers.

Elimination condition:

HP <= 0.

==================================================
8. WEAPONLESS FIGHTER
==================================================

READY fighter без Weapon:

- бере участь;
- є валідною ціллю;
- може отримувати damage;
- НЕ може атакувати.

Не видавати автоматично:

free pistol
melee attack
fists
fallback weapon.

Якщо обидві сторони більше не мають жодного fighter, здатного завдати шкоди:
Draw.

==================================================
9. HIT CHANCE
==================================================

Реалізувати configurable formula framework, де:

Fighter Accuracy
+
Weapon Accuracy contribution
-
Target Evasion from Agility/equipment

формують hit chance.

Prototype cap:

minimum 5%
maximum 95%

Це prototype values, але для milestone їх можна винести в RulesetConfig, а не hardcode по всьому коду.

Не робити critical hits.

==================================================
10. EVASION
==================================================

Agility впливає на evasion.

Не використовувати 1:1 пряме віднімання без configurable coefficients.

Formula coefficients повинні бути централізовані в battle rules/config.

==================================================
11. TEMPO / ACTION SCHEDULING
==================================================

Не використовувати просту round-robin чергу.

Реалізувати event/action-time simulation.

Кожен fighter має deterministic next-action timing.

Tempo залежить щонайменше від:

- Agility;
- weapon tempo/rate-of-fire value;
- equipment penalty, якщо передано в combat snapshot.

Battle core працює по simulated time, не по real wall-clock time.

==================================================
12. DAMAGE
==================================================

Базова структура:

Weapon Damage
× BB modifier
→ Raw Damage

після чого:

Armor / Protection
+
Penetration interaction
→ Effective Damage.

Не використовувати просту модель, де сильна armor легко зводить damage до 0 через flat subtraction.

Використати configurable mitigation approach.

==================================================
13. PENETRATION / PROTECTION
==================================================

Weapon/BB можуть мати penetration contribution.

Armor має protection.

Concept:

EffectiveProtection = max(0, Protection - Penetration)

після чого EffectiveProtection перетворюється в mitigation.

Конкретну функцію зробити:
- deterministic;
- bounded;
- configurable;
- протестованою.

Не дозволяти infinite/100% mitigation у нормальному діапазоні fixtures.

==================================================
14. BB MODEL
==================================================

BBs — shared team resource.

На один battle одна команда використовує один active BB tier.

Combat core приймає:

Attacker BB tier
Attacker BB budget

Defender BB tier
Defender virtual BB budget

==================================================
15. DEFENSE BB BUDGET
==================================================

Для defense fixtures правило вже затверджене:

virtual defense BB budget
=
100% максимальної BB capacity club snapshot.

Combat core не звертається до live inventory.

Caller передає finite defender budget.

==================================================
16. BB CONSUMPTION
==================================================

BB списуються за simulated projectiles.

Single shot:
відповідна кількість BB.

Burst:
списати число projectiles burst.

Shotgun:
pellet/projectile accounting має бути explicit.

Не створювати ammo з повітря.

Якщо BB недостатньо для planned attack:
визначити deterministic allowed behavior і покрити тестом.

Не робити negative ammo.

==================================================
17. NO-AMMO RULE
==================================================

Fighter/team без доступних BB:

не може виконувати ranged attack.

Якщо одна сторона ще може завдавати damage:
battle продовжується.

Якщо обидві сторони не можуть більше завдати damage:
Draw.

==================================================
18. DRAW RULES
==================================================

Підтримати Draw.

Draw occurs when:

1. simultaneous final elimination;
2. both sides can no longer make progress / deal damage;
3. Maximum Simulated Battle Duration reached without winner.

Не використовувати hidden Team Power tie-break.

==================================================
19. SIMULTANEOUS ELIMINATION
==================================================

Battle event resolution має бути визначена так, щоб genuinely simultaneous final elimination могла завершитись Draw.

Не вирішувати її випадково iteration order колекції.

Document exact deterministic event ordering / same-time resolution policy.

==================================================
20. SIMULATED TIME CAP
==================================================

Primary gameplay safety cap:

Maximum Simulated Battle Duration.

НЕ action-count gameplay cap.

MaxBattleDuration має бути configurable Ruleset value.

Точне final число не затверджене.

Для test/prototype fixtures вибери розумне temporary value і явно познач:

BALANCE HYPOTHESIS / PROTOTYPE CONFIG.

Якщо simulated time cap reached:
Draw.

==================================================
21. TECHNICAL EVENT GUARD
==================================================

Окремо реалізувати дуже великий technical event-count guard тільки як захист від:

bug
infinite loop
corrupt scheduling.

Це НЕ gameplay draw rule.

При його спрацюванні:
- deterministic failure/result path;
- explicit diagnostic;
- test.

Не маскувати bug як звичайний balance draw без логування.

==================================================
22. TARGET SELECTION
==================================================

Для v1 потрібна проста deterministic target-selection policy.

Не реалізовувати складний tactical AI.

Policy має:

- обирати тільки alive/valid targets;
- бути deterministic при одному seed;
- дозволяти small seeded variance;
- не залежати від unordered collection iteration.

Можна використати weighted choice / deterministic score.

Document decision.
